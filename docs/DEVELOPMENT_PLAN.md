# VolleyScope 開発計画

## 0. プロジェクトの個人的・実務的目的

本プロジェクトの出発点は、大学バレーボール部のコーチとして、大会当日に自チームへの指示、選手対応、試合準備と対戦相手分析を並行できず、撮影動画の事後集計にも大きな時間が必要だった実体験である。

単にAIモデルを利用した作品ではなく、NRI、CTC、ソニーセミコンダクタなどへの就職活動で、課題発見、関係者視点、要件定義、計画、仮説検証、批判的解釈、改善を一貫して説明できるガクチカ・ポートフォリオを目指す。

このため、各開発段階では成果物だけでなく、次を記録する。

- 誰のどの負担を減らす機能か
- なぜその作業を優先したか
- どの仮説をどの比較条件で検証したか
- 結果から言えることと言えないこと
- 代替案を採用しなかった理由
- 失敗または制約を次の改善へどう接続したか

## 1. この計画の目的

本計画は、VolleyScopeの最終構想を、個人開発として検証可能な作業単位へ分解するものです。

最終目標は、試合映像から選手・サーブ・トス・攻撃・守備のデータを自動生成し、戦術統計として可視化することです。ただし、映像中のボールを安定して追跡できなければ、後段のプレー分類や統計も正しくなりません。

そこで、次の因果関係に沿って開発します。

```text
撮影・データ品質
    ↓
選手・ボール検出
    ↓
フレーム間追跡
    ↓
コート座標・選手ID
    ↓
接触・プレー認識
    ↓
構造化イベント
    ↓
戦術統計・可視化
```

上流工程の誤差は下流へ伝播します。各段階に評価と移行条件を設け、基準を満たさない状態で次の高度な機能へ進まないことを基本方針とします。

## 2. 開発原則

### 2.1 最終出力から逆算する

「YOLOで何ができるか」から考えるのではなく、「コーチがどの統計を必要とするか」から必要データを逆算します。

例えば「相手7番のレフトからのクロス強打決定率」を出すためには、最低でも次の情報が必要です。

- 選手ID
- 攻撃位置
- 攻撃種別
- 攻撃コース
- 攻撃結果

必要情報を取得できない場合は、その統計を無理に生成しません。

### 2.2 完全自動化を目的にしない

人が数秒で正確に入力でき、AIでは大きな誤差が出る情報まで無理に自動化しません。

人の入力候補：

- コート四隅とネット位置
- チーム名と登録選手
- 初期ローテーション
- 最初の選手対応付け
- 低信頼度プレーの確認

AIが担当する価値が高い処理：

- 長時間動画の全フレーム処理
- ボール軌道の抽出
- 多数プレーの同一基準での分類
- 複数試合を横断した集計

### 2.3 評価できない機能は実装しない

各機能には正解データと評価指標を用意します。「見た感じ動く」だけでは完了としません。

### 2.4 不明を正解に見せない

各判定には信頼度と由来を保存します。

- `detected`: モデルが直接検出
- `tracked`: 追跡で推定
- `interpolated`: 欠損区間を補間
- `manual`: 人が入力・修正
- `unknown`: 判定不能

### 2.5 未知環境を最初から評価する

同じ試合の隣接フレームを学習・テストへ無作為に分けません。試合、体育館、撮影角度単位で分割し、未学習環境に対する性能を測ります。

## 3. スコープとリリース戦略

全機能を一度に実装すると、どの処理が失敗原因か特定できません。また、完成前に時間切れになる危険があります。そのため、縦に動く小さな完成版を順番に作ります。

### Release 0：検出・追跡検証版

動画から選手とボールを検出・追跡し、精度と失敗条件を測定します。

### Release 1：サーブ分析版

サーバー、サーブ種別、狙ったゾーン、結果を記録し、選手別のサーブ傾向を可視化します。

サーブから始める理由：

- プレー開始者が明確
- サーバーとボールの関係を限定しやすい
- コート外から開始するため位置を特定しやすい
- 出力する統計の実用価値が高い
- 攻守の複雑な接触連鎖より段階的に実装しやすい

### Release 2：アタック分析版

アタッカー、攻撃位置、強打・フェイント・プッシュ、コース、ワンタッチ、結果を記録・可視化します。

### Release 3：トス配分・守備分析版

セッターの条件付きトス配分と、相手の攻撃条件に対応した自チームの失点傾向を分析します。

### Release 4：複数試合統合版

複数試合を横断し、選手、ローテーション、得点状況、対戦相手別の傾向を比較します。

## 4. Phase 0：利用可能データと目的の確定

### 4.1 目的

モデル選定より先に、利用できる映像で最終目標を検証可能か判断します。動画不足、撮影角度不足、権利上の問題が後から判明すると、以降の作業が無駄になるためです。

### 4.2 実施内容

利用可能な動画ごとに、次のメタデータを記録します。

- 試合ID
- 体育館ID
- 撮影日
- 自チーム・対戦相手
- カメラ機種
- 解像度
- フレームレート
- 撮影位置
- 固定撮影か手持ちか
- コート全体が映っている割合
- 背番号の視認性
- ボールのおおよその画素サイズ
- 照明条件
- ユニフォームか練習着か
- 映像の利用・保存・公開可否

### 4.3 判断項目

- 異なる体育館の映像が複数あるか
- 未知環境テスト用の動画を確保できるか
- サーブ開始から落下まで映っているか
- アタック接触から落下まで映っているか
- 選手番号を識別できる画質か
- 動画をポートフォリオや発表で公開できるか

### 4.4 成果物

- `data/video_manifest.csv`
- 撮影条件一覧
- 動画利用ルール
- 実装対象と対象外の確定

### 4.5 移行条件

- 学習用と独立したテスト用試合を確保できる
- 少なくともボールと選手が目視可能
- 映像の利用範囲を説明できる

### 4.6 条件を満たさない場合

- 自分で固定条件の検証動画を撮影する
- 公開可能な動画はデモ専用、自身の動画は評価専用に分ける
- 最初の対象をサーブ練習映像へ限定する
- 選手識別を背番号ではなく手動IDへ切り替える

## 5. Phase 1：アノテーション仕様と正解データ

### 5.1 目的

AIが学ぶ正解を統一します。ラベルの定義が曖昧だと、モデル性能ではなくアノテーターの判断差を学習してしまいます。

### 5.2 物体検出ラベル

初期クラス：

- `ball`
- `player_court`
- `player_non_court`
- `net`

`player_court`と`player_non_court`を分ける理由は、ベンチ、審判、観客をプレー中の選手として集計しないためです。ただし、コート領域で後処理できる場合はperson一種類へ簡略化します。

ボールが完全に隠れているフレームには、推測で枠を付けません。一部が見えている場合の基準、モーションブラーで伸びたボールを囲む基準も仕様書に記載します。

### 5.3 イベントラベル

後段で追加する候補：

- サーブ種別
- サーブ落下ゾーン
- レセプション結果
- トス先
- 攻撃位置
- 強打・フェイント・プッシュ
- ストレート・クロス・インナー
- ワンタッチ
- ブロックアウト
- 得点・アウト・被ブロック・継続

### 5.4 主観的ラベルへの対応

強打、フェイント、プッシュ、レセプション評価などは、人間同士でも判断が分かれる可能性があります。

そのため、

- 定義文
- 典型例
- 境界例
- 判定不能例

を含むアノテーション仕様書を作成します。

可能であれば、一部を経験者2人が独立に分類し、一致率とCohenのκ係数を確認します。一致しない分類は、AIの問題にする前に定義を見直します。

### 5.5 サンプリング方法

30fps動画の全フレームを最初から囲むことはしません。

1. 複数動画から一定間隔で抽出
2. ボールが小さい、ぼける、隠れる場面を意図的に追加
3. 初期モデルを学習
4. 誤検出・低信頼度・追跡切断フレームを優先追加
5. 再学習

同じラリーの似たフレームだけでデータ数を増やさず、環境と失敗条件の多様性を優先します。

### 5.6 データ分割

フレーム抽出前に、元動画を次へ割り当てます。

- Train：モデル学習
- Validation：モデル・閾値選択
- Test-ID：既知環境に近い最終評価
- Test-OOD：未知体育館・未知角度の最終評価

Testデータはモデル改善中に繰り返し見て調整しません。

### 5.7 成果物

- `docs/ANNOTATION_GUIDE.md`
- 初期アノテーションデータ
- データ分割表
- ラベル分布表
- アノテーション品質確認結果

### 5.8 移行条件

- 主要ラベルを第三者が同じ基準で付けられる
- TrainとTest間に同一試合のフレームが混入していない
- 各環境条件のデータ数を説明できる

## 6. Phase 2：事前学習モデルのベースライン

### 6.1 目的

独自改良を加える前に、標準的なモデルで何ができ、何ができないかを定量化します。ベースラインがなければ、改良による効果を説明できません。

### 6.2 実施内容

- 事前学習済みYOLOを動画へ適用
- personとsports ballの検出結果を保存
- 誤検出・見逃しを条件別に分類
- 推論速度とメモリ使用量を測定
- 検出信頼度の閾値をValidationで調整

### 6.3 分析する失敗

- 照明、顔、看板をボールと誤検出
- 遠距離のボールを見逃す
- モーションブラー時に見失う
- 選手やネットとの重なりで見失う
- コート外人物を選手として検出

### 6.4 評価指標

- Precision
- Recall
- AP50
- mAP50–95
- 小物体AP
- 1分あたりの誤検出数
- フレーム単位のボール検出率
- 近距離・遠距離別Recall
- 遮蔽・ブラー別Recall
- 処理FPS

### 6.5 成果物

- ベースライン評価レポート
- 検出結果付き動画
- 誤検出・見逃し事例集
- 後続実験で改善すべき優先順位

### 6.6 移行条件

数値の高さではなく、失敗を再現可能な条件として分類できたことを移行条件とします。

## 7. Phase 3：バレーボール用検出モデル

### 7.1 目的

独自アノテーションを利用し、選手と高速・小物体であるボールの検出性能を改善します。

### 7.2 比較実験

一度に複数要素を変更せず、次の順に比較します。

| 実験 | 内容 | 確認する問い |
| --- | --- | --- |
| D0 | 事前学習モデル | 追加学習前の性能はどの程度か |
| D1 | 単一体育館で追加学習 | 対象環境ではどこまで改善するか |
| D2 | 複数体育館で追加学習 | 未知環境への性能低下を抑えられるか |
| D3 | 現実的なデータ拡張 | ブラー、照明、圧縮変化へ有効か |
| D4 | 高解像度・コート切り出し | 小さいボールのRecallが改善するか |
| D5 | P2などの小物体特徴 | 精度向上が計算量増加に見合うか |
| D6 | NWD系損失 | 小さい枠の位置ずれに有効か |

### 7.3 データ拡張

実環境で起こる変化に限定します。

- 輝度・コントラスト・色温度
- JPEG圧縮
- モーションブラー
- デフォーカス
- 縮小
- 部分遮蔽
- 現実的な範囲の遠近変形

強い拡張が常に有効とは限らないため、拡張なしとの比較を行います。

### 7.4 暫定目標

以下は成功を保証する基準ではなく、次段階へ進むための仮目標です。初回ベースラインの結果を見て改訂します。

- Test-IDでボールRecall 0.85以上
- Test-OODでボールRecall 0.70以上
- コート内選手Recall 0.90以上
- 誤ボール検出を1分あたり1件以下
- 既知環境から未知環境へのRecall低下率20%以内

### 7.5 基準未達の場合

- 撮影条件を標準化する
- 入力をコート領域へ限定する
- ボール専用検出器と選手検出器を分ける
- 全自動統計ではなく半自動補正を前提にする
- 最初の対象をサーブ映像へ限定する

## 8. Phase 4：追跡とコート座標

### 8.1 目的

フレームごとの検出を、ボール軌道と選手の連続した動きへ変換します。攻撃コースや落下位置は、追跡とコート座標がなければ計算できません。

### 8.2 実施内容

- ByteTrackなどによる選手追跡
- ボール専用の軌道追跡
- コート四隅の手動入力
- Homographyによるコート座標変換
- 一時的なボール消失の補間
- 検出値と補間値の区別

### 8.3 ボール追跡の注意点

ボールは高速で移動し、毎フレーム検出できるとは限りません。人物向けの一般的なトラッカーがそのまま最適とは限らないため、次を比較します。

- YOLO検出のみ
- YOLO＋一般トラッカー
- 軌道補間
- 速度・加速度・コート範囲などの制約

### 8.4 選手追跡の注意点

選手がネット付近で重なるとIDが入れ替わります。また、練習着では外観特徴が弱くなります。

対策候補：

- 背番号OCR
- 外観特徴
- コート上の位置
- ローテーション
- 手動初期ID
- ID喪失時の再指定
- 色付きビブスの利用

「常に自動識別」ではなく、「どの区間で識別を維持できたか」を測定します。

### 8.5 指標

- HOTA
- IDF1
- ID切り替わり数
- ボール軌道カバー率
- 平均・最長欠損フレーム数
- 誤った軌道接続数
- コートゾーン変換正解率

### 8.6 移行条件

- サーブ開始から落下までの軌道を十分な割合で復元できる
- 落下位置をコートゾーンへ変換できる
- 検出・追跡・補間の由来が保存されている

## 9. Phase 5：イベントデータ基盤

### 9.1 目的

映像を戦術統計へ直接変換せず、途中に共通のイベント形式を置きます。モデルを変更しても統計処理と画面を作り直さずに済むためです。

### 9.2 イベントの基本構造

```text
match_id
set_no
rally_id
team_id
player_id
rotation
skill
subtype
start_zone
target_zone
result
touch_type
confidence
source
review_status
```

### 9.3 内部的なラリー・接触分割

ユーザーへラリー時間を主要統計として表示することは目的ではありませんが、サーブ、レセプション、トス、アタックの順序を認識するため、内部的にはラリー単位へ分割します。

候補情報：

- サーバーとボールの接触
- ボールのネット通過
- ボールと選手の手・腕の接近
- 軌道方向・速度の急変
- ボールの落下
- 次のサーブ準備

### 9.4 成果物

- イベントスキーマ
- SQLiteデータベース
- 検出・追跡結果からイベント候補への変換処理
- 人がイベントを確認・修正する最小画面

## 10. Phase 6：サーブ分析

### 10.1 目的

最初の戦術分析機能を端から端まで完成させます。検出、追跡、分類、保存、集計、可視化の全工程をサーブで検証します。

### 10.2 分類項目

- サーバー
- スタンディングフローター
- ジャンプフローター
- ジャンプトップスピン
- その他・判定不能
- サーブ開始位置
- 狙った・落下したゾーン
- レシーバー
- エース
- レセプションを崩した
- インプレー
- ミス

### 10.3 認識方法

サーブ種別は単一フレームのYOLOではなく、次を入力にした時系列分類として扱います。

- 選手の助走
- ジャンプの有無
- トス位置
- 接触位置
- 腕の動き
- ボール軌道

通常の試合映像ではボール回転を正確に測れない可能性が高いため、回転を必須特徴にはしません。

### 10.4 出力

- 選手別サーブ種別比率
- 狙ったゾーンのヒートマップ
- エース率・ミス率
- レセプションを崩した割合
- ローテーション・得点状況別傾向
- 定量的なビッグサーバー特性

### 10.5 評価

- サーブ種別Macro-F1
- 落下ゾーン正解率
- サーバー識別率
- 結果分類Macro-F1
- 手作業集計との割合誤差
- 1試合の確認時間削減率

### 10.6 暫定移行条件

- サーブ種別Macro-F1 0.75以上
- 落下ゾーン正解率0.80以上
- 選手別構成比の誤差10ポイント以内
- 手作業より確認時間を50%以上削減

基準未達でも、誤りが特定クラスへ集中し、人による確認で実用化できる場合は半自動版としてRelease 1を成立させます。

## 11. Phase 7：アタック分析

### 11.1 目的

選手ごとの得点手段とコースを構造化し、相手攻撃への守備判断に使える情報を生成します。

### 11.2 分類項目

- アタッカー
- レフト・センター・ライト・バックアタック
- 強打・フェイント・プッシュ
- ストレート・クロス・インナー
- 詳細な落下位置
- ブロッカー数
- ワンタッチ有無
- 直接得点
- ワンタッチ後の得点
- ブロックアウト
- レシーバーが弾いた得点
- 被ブロック
- アウト
- 継続

### 11.3 なぜ難しいか

- ボールと手が重なる
- ブロック接触が小さく見える
- ワンタッチ後の軌道変化が僅かな場合がある
- フェイントとプッシュの定義に主観が入る
- 単一カメラでは奥行きが失われる

したがって、最初にすべてを同じ難易度で扱いません。

実装順：

1. 攻撃位置
2. アタッカー
3. 落下位置・コース
4. 攻撃結果
5. 強打・フェイント・プッシュ
6. ワンタッチ・ブロックアウト

### 11.4 出力

## 16. リスクと対策

| リスク | 影響 | 早期確認方法 | 対策 |
| --- | --- | --- | --- |
| ボールが小さすぎる | 全分析が成立しない | Phase 2ベースライン | 高解像度、撮影標準化、専用検出器 |
| 未知体育館で精度低下 | 実運用できない | Test-OODを分離 | 複数環境学習、拡張、少数適応 |
| 選手IDが入れ替わる | 個人統計が崩れる | ID切替数を測る | 初期指定、背番号、ローテーション、再指定 |
| 練習着で識別不能 | 個人分析不能 | 練習映像で検証 | ビブス、手動ID、チーム単位分析 |
| 主観ラベルが不一致 | 学習・評価が不安定 | 複数人で一部ラベル | 定義見直し、判定不能クラス |
| アノテーション量が過大 | 開発が停止 | 100枚当たり時間計測 | 仮ラベル、追跡伝播、難例優先 |
| 高精度だが処理が遅い | 大会中に使えない | 動画1分当たり時間 | オフライン前提、モデル軽量化 |
| 全機能を広げすぎる | 何も完成しない | リリース単位で評価 | サーブ版を最初の完成品にする |
| 動画を公開できない | 成果を提示しにくい | Phase 0で権利確認 | 公開用再現動画、匿名化、統計のみ公開 |

## 20. 成功の定義

VolleyScopeの成功は、すべてのプレーを100%自動認識することではありません。

次の三点を満たすことを成功と定義します。

1. 映像から戦術データを生成する処理が、未知環境を含めて定量評価されている
2. AIが判断できる範囲と、人の確認が必要な範囲が明確である
3. 手作業と比較して、コーチが同等の戦術的傾向を短時間で把握できる

この定義により、モデル精度だけでなく、実際の課題解決と説明可能性を重視します。

## ボール検出モデルの再検討

事前学習済みYOLO11nの評価により、遮蔽なし画像でもRecallが47.8%、遮蔽なしで小さい半分に限定すると21.7%だった。

この結果から、最初に視認可能な小物体の基本検出性能を改善する。

ボール検出モデルをYOLOへ固定せず、以下を比較する。

- バレーボールデータで追加学習したYOLO
- 小物体向け検出ヘッドを持つモデル
- 複数の連続フレームを利用するTrackNet系モデル

システム内の責務を次のように分離する。

- 選手・ネット・コート：YOLO系モデル
- ボール：YOLO追加学習版とTrackNet適応版を比較
- 軌道補完：基本検出性能を確立した後に実装
- 戦術分類：検出・追跡結果を時系列データへ変換した後に実装

### TrackNetV3の導入方針

事前調査の結果、TrackNetV3はMIT Licenseで公開重みもあり、出力形式もフレームごとの座標へ変換しやすいため、比較候補として導入可能と判断した。

一方、公式環境はPython 3.8.7とPyTorch 1.10.0であり、依存定義の不足、`.cuda()`固定、データパス固定、任意チェックポイントからのファインチューニング機能不足がある。そのため、公式コードの全面統合や全面再実装は行わず、追跡モジュールの推論部分を専用環境へ小さく移植して評価する。

実施順序は次のとおりとする。

1. Pythonを導入し、YOLOとは別のTrackNet専用仮想環境を作る
2. 現行PyTorchとGPUで公式公開重みを読み込めるか確認する
3. TrackNet単体を`batch_size=1`で短いVolleyScope動画へ推論する
4. VRAM使用量、FPS、出力座標、目視可能な小球の見逃しを記録する
5. 連続フレーム評価データとYOLO・TrackNet共通評価器を作る
6. 有望な場合だけ、バレーボール用ファインチューニング入口を追加する
7. 基本検出性能の確立後にInpaintNetを評価する

4GB VRAMのため、学習の可否は設定から推測せず実測する。ローカル学習が困難な場合は、推論と評価をローカル、学習をクラウドGPUへ分離する。

専用環境ではPython 3.12.10、PyTorch 2.7.1+cu118を採用し、公開重みを使った疑似入力推論に成功した。公式のPython 3.8.7、PyTorch 1.10.0を再現する方針ではなく、現行環境へ必要箇所だけ移植する。互換性変更は実験記録へ残し、先行研究の再現実験とVolleyScope向け適応実験を区別する。


### TrackNetV3評価データの構成方針

既存の`evaluation_001`は約4〜5フレーム間隔で抽出された静止画であるため、その150枚をそのままTrackNetV3の入力系列には使用しない。

一方、画像ファイル名と`manifest.csv`には元動画のフレーム番号が記録されている。そのため、アノテーション済みフレームを評価対象とし、周辺の連続フレームを元動画から読み出すことで、既存の正解ラベルをTrackNetV3の評価へ再利用する。

ただし、TrackNetV3公式実装における連続8フレームの入力と8枚の出力の時間的な対応、および動画先頭・末尾における不足フレームの扱いは、公式コードを確認してから決定する。

### YOLOとTrackNetV3の公平比較方針

YOLOとTrackNetV3の比較では、両モデルへ同じ動画から読み出した同一フレームを入力する。

YOLOは矩形、TrackNetV3はヒートマップという異なる形式で結果を出力する。そのため、両方の結果をフレームごとのボール中心座標へ変換し、共通形式で評価する。

比較指標の候補は次のとおりとする。

- Precision
- Recall
- F1
- 正解中心点と予測中心点の距離
- 許容距離内の検出率
- 処理速度
- 連続検出の安定性

矩形の重なりを測るIoUだけでは、点に近いTrackNetV3の出力をYOLOと公平に比較できない可能性がある。そのため、VolleyScopeの最終目的である軌道・落下位置推定へ直接関係する中心点誤差を重視する。

公式コードは`C:\GitHub\TrackNetV3-reference`へ参照用として分離し、コミット`77c123ad4dd449b7d275f16cc43f316ba5b54042`に固定する。公式リポジトリ全体をVolleyScopeへ取り込まず、仕様を確認したうえで必要な推論処理だけを移植する。

最初に非重複8フレーム系列でモデル本体の推論を成立させ、その後に1フレームずつ移動する重複系列とTemporal Ensembleを追加する。これにより、モデル本体と時系列アンサンブルの影響を分けて評価する。

背景中央値生成は元解像度フレームを大量に保持する可能性があるため、実行前にCPUメモリ使用量を見積もる。必要に応じて、サンプル数の削減、リサイズ後の中央値計算、事前計算した背景画像の再利用を比較する。

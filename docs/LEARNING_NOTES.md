# 2. `.gitignore`

`.gitignore`は、Gitの管理対象に含めないファイルやフォルダを指定する設定ファイルである。

VolleyScopeでは、以下をGitHubへアップロードしない。

```gitignore
.venv/
__pycache__/
*.pyc

data/raw/
data/clips/
data/frames/
outputs/

*.mp4
*.mov
*.avi
*.mkv

*.pt
*.onnx
```

対象外にする理由：

- `.venv`：PCごとに作り直せるPython環境
- `data/raw`：公開許可や個人情報の問題がある試合動画
- `data/frames`：動画から大量生成される画像
- `outputs`：再生成できる解析結果
- 動画ファイル：容量が大きい
- 学習済みモデル：容量が大きい

`.gitignore`はGitHubへの登録を防ぐが、OneDriveへの同期は防がない。

`.venv`は、VolleyScope専用のPythonとライブラリを保存するフォルダである。

仮想マシンや別のWindowsを作っているわけではない。

```text
VolleyScope/
```


```powershell
.\.venv\Scripts\python.exe
```

# 7. `-m`の意味

# 10. Pythonのインデント

Pythonでは、インデントによって処理の所属範囲を表す。

```python
def main():
    print("mainの中")
    print("これもmainの中")
```

# 11. 関数

関数は、複数の処理を一つの名前でまとめたものである。

```python
def main():
    print("動画を確認します")
```

`def main():`は、`main`という処理を定義しているだけで、まだ実行していない。

実際に処理を実行するには、関数を呼び出す。

```python
main()
```

`main`という名前自体に特別な動作はない。「プログラムの中心処理」という意味で一般的に使用される名前である。

# 12. `__name__`と`__main__`

`__name__`は、Pythonがモジュールへ自動設定する特別な変数である。

Pythonファイルを直接実行した場合：

```python
__name__ == "__main__"
```

別のPythonファイルからimportした場合：

```python
__name__ == "ファイル名"
```

そのため、次のコードを利用する。

```python
if __name__ == "__main__":
    main()
```

日本語にすると、

> このファイルがプログラム本体として直接実行された場合だけ、main関数を実行する

という意味になる。

別ファイルからimportされた場合は条件が成立せず、`main()`は実行されない。

# 15. OpenCVによる動画読み込み

動画を開く処理：

```python
video = cv2.VideoCapture(str(VIDEO_PATH))
```

ファイルがOpenCVで正常に開けたか確認する。

```python
if not video.isOpened():
    print("動画を開けませんでした")
    return
```

動画情報を取得する。

```python
width = int(video.get(cv2.CAP_PROP_FRAME_WIDTH))
height = int(video.get(cv2.CAP_PROP_FRAME_HEIGHT))
fps = video.get(cv2.CAP_PROP_FPS)
frame_count = int(video.get(cv2.CAP_PROP_FRAME_COUNT))
```

| 項目 | 意味 |
|---|---|
| width | 横方向の画素数 |
| height | 縦方向の画素数 |
| FPS | 1秒間に含まれるフレーム数 |
| frame_count | 動画全体のフレーム数 |

動画時間は、総フレーム数をFPSで割って求める。

```python
duration_seconds = frame_count / fps
```

処理後は動画ファイルを解放する。

```python
video.release()
```

# YOLOによる推論と比較実験

## 1. データセット・モデル・重みの違い

この3つは関係しているが、それぞれ異なるものである。

### データセット

データセットとは、モデルの学習や評価に使用するデータの集まりである。

物体検出の場合は、主に次の情報が含まれる。

- 画像
- 画像内に存在する物体の種類
- 物体を囲む正解の枠
- 学習用、検証用、テスト用の区分

つまり、データセットは「モデルに問題と正解を与える教材」に相当する。

### モデル

モデルとは、画像を入力として受け取り、画像内に何がどこに存在するかを計算する仕組みである。

今回使用しているYOLO11nは、物体検出を行うモデルの一つである。

### 重み

重みとは、モデルが学習によって獲得した数値の集まりである。

モデルの構造が同じでも、異なるデータセットで学習すれば、異なる重みになる。

今回使用した`yolo11n.pt`には、COCOデータセットを使って事前に学習された重みが保存されている。

---

## 2. COCOデータセットとは

COCOは、物体検出などの研究や開発で広く利用されているデータセットである。

人物、自動車、犬、椅子、スポーツボールなど、日常的な物体のクラスが含まれている。

今回使用したYOLO11nは、COCOを使って事前学習されている。そのため、自分でまだバレーボール映像をアノテーションしていない状態でも、次のような物体を検出できる。

- 人物
- スポーツボール

ただし、COCOのスポーツボールには、バレーボール以外の種類やさまざまな撮影環境が含まれている。そのため、バレーボール試合映像に特化した検出能力が保証されているわけではない。

なお、今回COCOデータセット全体をパソコンへダウンロードしたわけではない。COCOで学習された結果を持つ`yolo11n.pt`を利用している。

---

## 3. 事前学習済みモデルとは

事前学習済みモデルとは、すでに別のデータセットで学習された重みを持つモデルである。

今回の開発では、次の状態から実験を開始した。

```text
COCOデータセット
        ↓ 学習済み
YOLO11nの重み（yolo11n.pt）
        ↓ バレーボール動画を入力
検出結果を出力
```

現段階では、自分でアノテーションしたデータを使ってYOLOを学習させたわけではない。

まず事前学習済みモデルをそのまま使用し、何ができて何ができないかをベースラインとして確認している。

このベースラインがあることで、将来自分のデータで追加学習した際に、どの程度性能が改善したか比較できる。

---

## 4. `.pt`ファイルと`.gitignore`

`yolo11n.pt`の`.pt`は、PyTorchで使用されるモデルの重みを保存するファイル形式である。

`.gitignore`に次のように書かれている場合、

```gitignore
*.pt
```

`*`は任意のファイル名を表す。そのため、「末尾が`.pt`であるすべてのファイルをGitの管理対象から外す」という意味になる。

これはファイルをパソコンから削除する設定ではない。また、プログラムから使用できなくなるわけでもない。

次のような状態になる。

```text
自分のパソコン：yolo11n.ptが存在し、使用できる
GitHub：yolo11n.ptを送信しない
```

モデルの重みはファイルサイズが大きくなる場合があり、公開済みの重みは再度ダウンロードできる。そのため、通常のGit管理から除外することがある。

---

## 5. 推論とは

推論とは、学習済みモデルへ新しいデータを渡し、学習済みの重みを使って判定結果を出す処理である。

今回の場合は、バレーボール動画をYOLO11nへ入力し、人物やスポーツボールの位置と信頼度を出力する処理が推論に該当する。

```text
学習
画像と正解ラベルをモデルへ渡す
        ↓
モデルの重みを更新する

推論
新しい画像や動画を学習済みモデルへ渡す
        ↓
学習済みの重みを使って検出結果を出す
```

推論時に指定する`conf`や`imgsz`は、モデルに新しい知識を学習させる条件ではなく、学習済みモデルをどのような条件で使用するかを指定する設定である。

---

## 6. `predict()`とは

`predict()`は、UltralyticsのYOLOモデルを使って推論を実行するためのメソッドである。

例：

```python
results = model.predict(
    source=VIDEO_PATH,
    conf=0.25,
    imgsz=960,
)
```

主な設定の意味は次のとおりである。

- `source`：解析する画像や動画
- `conf`：結果として採用する最低信頼度
- `imgsz`：推論時に使用する入力画像サイズ
- `classes`：検出対象とするクラス
- `save`：枠を描画した結果を保存するか
- `project`：出力先の親フォルダ
- `name`：実験結果を保存するフォルダ名
- `save_txt`：検出結果をテキストとして保存するか
- `save_conf`：テキストへ信頼度も保存するか
- `stream`：動画の結果を一度に保持せず、順番に処理するか

`predict()`は「解析条件を書くだけのもの」ではない。引数によって解析条件を指定し、その条件に従って実際に推論を実行する処理である。

---

## 7. 信頼度と`conf`

YOLOは検出候補ごとに、「その物体である可能性をモデルがどの程度高く見積もったか」を示す信頼度を出力する。

`conf=0.25`は、信頼度が0.25以上の候補を結果として採用する設定である。

しきい値を低くすると、弱い候補も結果に含まれるため、見逃しを減らせる可能性がある。一方で、誤検出も増えやすい。

しきい値を高くすると、強い候補だけが残るため、誤検出を減らせる可能性がある。一方で、本物のボールも除外される可能性がある。

したがって、信頼度しきい値には次のトレードオフがある。

```text
confを下げる
検出候補が増える
見逃しが減る可能性がある
誤検出が増える可能性がある

confを上げる
検出候補が減る
誤検出が減る可能性がある
見逃しが増える可能性がある
```

---

## 8. `imgsz`とは

`imgsz`は、YOLOが推論するときに使用する入力画像サイズを指定する設定である。

元動画の解像度そのものを書き換える設定ではない。YOLOへ入力する際に、解析用として画像サイズを調整する。

小さなボールは、入力画像を縮小した際に数ピクセル程度になり、特徴が失われる可能性がある。入力画像サイズを大きくすると、小さな物体の情報が残りやすくなる場合がある。

一方で、入力画像サイズを大きくすると、次の問題も発生する。

- 計算量が増える
- 処理時間が長くなる
- 使用メモリが増える
- ボールと似た小物体も検出候補になる可能性がある

今回の実験では、画像サイズを大きくすることで本物のボールの検出が増えた一方、選手のシューズに対する誤検出も増えた。

---

## 9. `perf_counter()`とは

`perf_counter()`は、Pythonの標準ライブラリ`time`にあらかじめ用意されている、処理時間を精密に測るための関数である。

自分で作成した関数名ではない。

次のように読み込んで使用する。

```python
from time import perf_counter
```

処理前と処理後に値を取得し、その差を計算する。

```python
start_time = perf_counter()

# 計測したい処理

elapsed_seconds = perf_counter() - start_time
```

それぞれの名前は次のように分類できる。

- `perf_counter`：Python側で定義されている関数
- `start_time`：開発者が付けた変数名
- `elapsed_seconds`：開発者が付けた変数名

`perf_counter()`が直接「処理時間」を返すわけではない。基準となる時点から進んだ高精度な時間を返すため、開始前後の差を取って経過時間を求める。

## 10. 出力先の決まり方

例えば、コードに次の設定がある場合、

```python
OUTPUT_ROOT = PROJECT_ROOT / "outputs"
```

出力先の親フォルダを`outputs`に設定している。

さらに、`predict()`で次のように指定する。

```python
model.predict(
    project=str(OUTPUT_ROOT),
    name="baseline_yolo11n",
    save=True,
)
```

各設定の役割は次のとおりである。

```text
project = outputs
name = baseline_yolo11n
        ↓
outputs/baseline_yolo11n
```

`save=True`によって、検出枠が描画された結果が保存される。

したがって、出力先は一つの記述だけで決まるのではなく、主に`project`と`name`の組み合わせによって決まる。

## 11. 検出数と精度は同じではない

検出フレーム数が多い場合でも、そのすべてが本物のボールとは限らない。

今回の実験では、次のものがボールとして誤検出された。

- 動画内の赤い再生位置マーカー
- 選手の頭
- 選手のシューズ

したがって、単純に検出数が増えたことだけを根拠に、モデルの性能が向上したと判断してはいけない。

検出結果を評価するためには、最低でも次の2点を分けて考える必要がある。

- 本物のボールをどの程度見つけられたか
- ボールではない物体をどの程度誤検出したか

## 12. PrecisionとRecall

### Precision

Precisionは、モデルがボールとして検出したもののうち、実際にボールだった割合である。

```text
Precision
= 正しく検出したボール
  ÷ ボールとして検出したすべての候補
```

シューズなどの誤検出が増えると、Precisionは低下する。

### Recall

Recallは、実際に存在していたボールのうち、モデルが発見できた割合である。

```text
Recall
= 正しく検出したボール
  ÷ 本来検出すべきだったボール
```

本物のボールを見逃すと、Recallは低下する。

PrecisionとRecallを正しく計算するためには、人間が作成した正解データが必要である。

## 13. 検出フレーム率とRecallの違い

今回計算した検出フレーム率は、次の計算である。

```text
ボールクラスの枠が出たフレーム数
÷ 処理した全フレーム数
```

これはRecallではない。

動画には、ボールが映っていないフレームや、選手などに完全に隠れているフレームも含まれる。また、ボールクラスの枠がシューズなどに付いている可能性もある。

Recallを計算するには、各フレームについて本物のボールが存在するか、どこに存在するかを示す正解ラベルが必要になる。

## 8. TP・FP・FN

### TP（True Positive）

本物のボールを正しく検出した結果。

### FP（False Positive）

シューズなど、ボールではない物体をボールとして検出した結果。

### FN（False Negative）

存在する本物のボールを検出できなかった結果。

物体検出では、ボールがない画像の背景領域を無数に数えられるため、通常は物体単位のTNを主要指標として使用しない。今回は補助的に、ボールなし画像で誤検出がなかった件数を画像単位で確認した。

## 9. Precision・Recall・F1

### Precision

```text
Precision = TP ÷ (TP + FP)
```

検出した候補のうち、本物だった割合である。

### Recall

```text
Recall = TP ÷ (TP + FN)
```

実際に存在したボールのうち、発見できた割合である。

### F1

```text
F1 = 2 × Precision × Recall
     ÷ (Precision + Recall)
```

PrecisionとRecallの調和平均であり、両方のバランスを表す。

## 型注釈とPylance

次の型注釈は、辞書のキーが文字列であり、値には文字列または整数が入ることを表す。

```python
row: dict[str, str | int]
```

型注釈がない状態では、Pylanceが最初の値だけを見て、辞書の値はすべて文字列だと推測した。その後、0または1の整数を代入したため警告が表示された。

型注釈はプログラムの処理を変更するものではない。コードが想定しているデータ型を、人間と静的解析ツールへ明示する役割を持つ。

## 正規化座標からピクセル数への変換

YOLO形式のラベルでは、枠の幅と高さが画像全体に対する比率で保存される。

```text
クラス 中心X 中心Y 幅 高さ
```

実際の幅と高さは次のように計算できる。

```text
枠の幅px = 正規化された幅 × 画像の横幅
枠の高さpx = 正規化された高さ × 画像の高さ
枠の面積px² = 枠の幅px × 枠の高さpx
```

## 四分位グループ

データを小さい順に並べ、件数がほぼ同じ4グループへ分ける方法である。

ただし、境界値がデータに依存するため、別の試合でも同じ境界が有効とは限らない。

## Wilson信頼区間

成功率とサンプル数から、真の成功率が存在すると考えられる範囲を推定する方法である。

同じRecall 50%でも、2枚中1枚と100枚中50枚では結果の確実性が異なる。Wilson信頼区間を使うことで、グループの件数が少ない場合の不確実性を表現できる。

信頼区間は「真の値が必ずこの中にある確率」を直接表すものではなく、同じ手順で標本抽出と区間推定を繰り返したとき、その95%程度が真の値を含むよう設計された区間である。

## UTF-8と文字化け

文字コードは、文字と保存される数値の対応規則である。

UTF-8で保存された日本語をPowerShellが別の文字コードとして解釈すると、ファイルが壊れていなくても文字化けする場合がある。

各要素の意味は次のとおりである。

## 動画のフレーム番号と時刻

```text

```

約62 FPSの動画では、4フレーム分の時間は次のように計算できる。

```text

```

今回の評価画像は約4〜5フレーム間隔で抽出されているため、TrackNetV3が必要とする連続フレームではない。

## TrackNetV3実動画スモークテストで学んだこと

### スモークテスト

スモークテストは、詳細な精度評価の前に、構成要素を最低限接続して処理が最後まで動くか確かめる検証である。

今回確認した処理の流れは次のとおりである。

```text
実動画
  ↓
公式前処理
  ↓
27チャンネル入力
  ↓
TrackNetV3
  ↓
8枚のヒートマップ
  ↓
元解像度の座標
```

最後まで実行できても、精度が実用水準に達したことにはならない。

```python
import argparse
```

`argparse`は、PowerShellなどから渡されたコマンドライン引数を解析する標準ライブラリである。

実験条件をコマンドとして明示できるため、再現性を高められる。

#### sys


`sys`は、Python実行環境に関する機能を提供する標準ライブラリである。

今回は参照用TrackNetV3リポジトリを`sys.path`へ一時的に追加し、公式コードをVolleyScopeへコピーせずに読み込むために使用した。

`Path`は、ファイルやディレクトリのパスをオブジェクトとして扱う標準ライブラリである。

今回はプロジェクト位置を基準に入力動画とチェックポイントの場所を組み立て、ファイルやディレクトリが存在するか検証するために使用した。

#### time.perf_counter


`perf_counter`は、短い処理時間の測定に適した高精度タイマーである。

今回はGPU推論の開始前後を測定した。

ただし、GPU処理は非同期に実行されるため、測定前後に`torch.cuda.synchronize()`を実行して処理完了を待つ必要がある。

#### torch

```python
import torch
```

`torch`はPyTorchを読み込み、テンソル操作、モデル構築、チェックポイント読み込み、GPU推論などを可能にする。

今回は次の処理に使用した。

- NumPy配列をテンソルへ変換する
- 入力をGPUへ移動する
- 公開チェックポイントを読み込む
- 勾配計算を無効化して推論する
- 出力にNaNや無限大がないか確認する
- ヒートマップの最大位置を取得する
- GPUメモリ使用量を測定する

### sys.pathと外部コードの参照

Pythonは通常、実行ファイルの周辺やインストール済みパッケージからimport対象を探す。

```python
sys.path.insert(0, tracknet_root_text)
```

この処理は、参照用TrackNetV3リポジトリを探索対象の先頭へ一時的に追加する。

公式コードを複製せず、固定コミットのまま参照できる。一方、同名モジュールが存在すると意図しないファイルを読み込む可能性がある。

そのため、参照先のパスとGitコミットを実験記録へ残す必要がある。

### torch.loadの互換性

```python
checkpoint = torch.load(
    checkpoint_path,
    map_location="cpu",
    weights_only=False,
)
```

`map_location="cpu"`は、チェックポイントを最初からGPUへ配置せず、CPU上で読み込む指定である。

`weights_only=False`は、現在のPyTorchで旧形式のチェックポイント全体を読み込むために明示した。

信頼できないチェックポイントへ指定すると任意コード実行の危険があるため、入手元を確認した公式ファイルに限って使用する。

### model.evalとtorch.inference_mode

```python
model.eval()
```

`eval()`はモデルを推論モードへ切り替える。

DropoutやBatch Normalizationなど、学習時と推論時で動作が変わる層へ影響する。

```python
with torch.inference_mode():
    output = model(input_tensor)
```

`inference_mode()`は推論中の勾配記録を無効にし、不要なメモリ使用と計算を減らす。

`eval()`と`inference_mode()`は役割が異なるため、推論では両方を使用する。

### GPU処理時間の測定

GPUの処理は、CPUから命令を渡した直後に完了しているとは限らない。

そのため、次の順序で時間を測定した。

```python
torch.cuda.synchronize()
start_time = perf_counter()

with torch.inference_mode():
    output = model(input_tensor)

torch.cuda.synchronize()
elapsed_seconds = perf_counter() - start_time
```

最初の`synchronize()`は、測定開始前に残っているGPU処理の完了を待つ。

後の`synchronize()`は、今回の推論が完了してから終了時刻を取得するために使用する。

ただし、1回ごとの推論時間には初期化、GPUの状態、他の処理などの影響がある。安定したFPSを求めるには、ウォームアップ後に複数回測定する必要がある。

### 公式しきい値とヒートマップ最大位置

公式処理では、ヒートマップの各画素について次の判定を行う。

```python
output > 0.5
```

これはYOLOの物体単位のconfidenceと同じ意味ではない。

TrackNetV3が出力した各画素の値を二値化するしきい値である。

すべての画素が0.5以下なら、公式処理では未検出になる。一方、最大位置を調べると、0.5未満でもモデルが最も強く反応した場所を確認できる。

最大位置が正解から遠い場合、しきい値を下げるだけでは正しい検出にならない。誤った場所の反応まで検出として採用する可能性があるためである。

### argmaxとdivmod

```python
flat_peak_index = frame_heatmap.argmax().item()
peak_y, peak_x = divmod(
    flat_peak_index,
    heatmap_width,
)
```

`argmax()`は、ヒートマップ内で最大値を持つ要素の位置を、一次元化された番号として返す。

`divmod(一次元番号, 横幅)`は、商と余りを同時に返す。

- 商：縦方向の位置`y`
- 余り：横方向の位置`x`

これにより、一次元の最大位置を二次元画像上の座標へ戻せる。

### ゼロショット結果とモデル構造の評価

バドミントン用公開重みを、追加学習せずバレーボールへ適用することを、今回のゼロショット転用として扱う。

ゼロショット転用の失敗から分かるのは、現在の公開重みが対象映像へ適合しなかったことである。

TrackNetV3の構造をバレーボール用に追加学習した場合の性能までは判断できない。

次の二つを混同しない。

```text
公開重みの直接転用が失敗した
≠
TrackNetV3の構造がバレーボールに不適切である
```

### 同一動画内のデータ分割

現在の段階では、YOLOとTrackNetV3を同じ動画・同じ条件で比較する。

ただし、隣接フレームは見た目が非常に似ている。同一またはほぼ同一の場面を学習と評価へ分けると、モデルが未知のボールを検出したのか、似た画像を記憶したのか区別しにくい。

そのため、フレームをランダムに混ぜるのではなく、時間的に連続した区間を単位として学習・検証・評価へ分割する。

この比較から主に言えるのは、現在の撮影条件内における両モデルの違いである。

未知環境への汎化は、その後の独立した検証課題とする。

## TrackNetV3学習データ設計で学んだこと

### TrackNetV3の正解ラベル

TrackNetV3公式実装は、フレームごとに次の情報を使用する。

```text
Frame, Visibility, X, Y
```

YOLOの正規化中心座標は次の計算で元解像度へ戻せる。

```text
X = x_center × image_width
Y = y_center × image_height
```

TrackNetV3は矩形の幅と高さではなく、中心座標から正解ヒートマップを生成する。

ボールなしフレームでは、`Visibility=0`だけでなく`X=0`かつ`Y=0`を保証する必要がある。公式コードは座標が両方0の場合に、全画素0の正解ヒートマップを生成するためである。

### 連続窓と独立データ数

128枚へ系列長8、sliding step 1を適用すると、121系列を生成できる。

```text
128 - 8 + 1 = 121
```

ただし、隣り合う系列は7枚を共有する。したがって、121系列を121件の独立した動きとして解釈してはいけない。

### 公式preprocess.pyの副作用

`shutil.move`はファイルをコピーするのではなく移動する。

公式前処理では、各matchの最後のラリーをtrainからvalへ移動する。実行前後でデータ配置が変わるため、VolleyScopeでは明示的なsplit manifestから別出力先へデータを生成する。

### 半開区間

抽出範囲は次の形式で管理する。

```text
start_frame <= frame_index < end_frame_exclusive
```

終了フレームを含めないことで、枚数を次の引き算で求められる。

```text
frame_count = end_frame_exclusive - start_frame
```

### 抽出成功とデータ妥当性の違い

プログラムが予定枚数を保存しても、プレー区間を抽出できたとは限らない。

今回、35秒から64枚の抽出は機械的には成功したが、目視確認でプレー場面ではないと判明した。

そのため、データ作成では次の両方が必要である。

- 機械的検証：枚数、連続性、欠落、重複、パス
- 意味的検証：プレー内容、ボールの存在、動き、画角、画像破損

### 画像類似度による時刻推定の限界

固定カメラの体育館映像では、背景が長時間似ている。少数の縮小グレースケール画像について平均絶対誤差を最小化しても、正しい時刻を保証できない。

類似度の1位候補は仮説生成には使えるが、生成履歴、manifest、直接照合、目視確認より強い証拠として扱わない。

## 共通アノテーションから複数モデル用ラベルを作る

YOLO形式は次の5列である。

```text
class_id x_center y_center width height
```

中心座標と矩形サイズは0〜1へ正規化されている。

TrackNetV3形式は次の4列である。

```text
Frame,Visibility,X,Y
```

YOLO中心座標からTrackNetV3座標へ変換できる。

```text
X = x_center × image_width
Y = y_center × image_height
```

### 負例の表現

Label Studioで矩形なしのままSubmitすると、YOLOエクスポートでは0バイトのラベルファイルになる。

この空ファイルを次へ変換する。

```text
Visibility=0
X=0
Y=0
```

`Skip`は未判断と区別しにくいため使用しない。

### 部分遮蔽と完全遮蔽

部分遮蔽でも物理的なボール中心を判断できる場合は正例とする。

完全遮蔽で中心を判断できない場合は、前後フレームから推測して座標を付けず、不可視として記録する。

観測できる位置と、時系列モデルが推定する位置を混同しない。

### 数値検証と目視検証

座標が範囲内で滑らかでも、実際のボール中心から一貫してずれている可能性がある。

そのため、次の両方を行う。

- 数値検証：行数、クラス、値域、可視性、座標、重複
- 目視検証：変換座標を元画像へ重ねて中心位置を確認

### 四捨五入規則

座標変換では、0以上の値に対して次を使用した。

```python
int(value + 0.5)
```

これにより、小数部分が0.5以上なら切り上げる規則を明示できる。


## 連続軌道アノテーションと再利用可能な可視化

### 物理的な存在と教師ラベル上の可視性

映像内にボールが存在していても、中心座標を合理的に判断できるとは限らない。

ボール中心を判断できる場合は`Visibility=1`としてX座標とY座標を記録する。完全遮蔽などで中心を判断できない場合は`Visibility=0, X=0, Y=0`とする。

不可視座標を前後フレームから推測すると、人間の想像を正解として学習させることになる。そのため、観測ラベルと軌道補間は分けて扱う。

### 部分遮蔽時の矩形

見えている断片だけを囲むと、矩形中心が物理的なボール中心からずれる可能性がある。

TrackNetV3用座標では矩形サイズより矩形中心が重要である。部分遮蔽でも中心を判断できる場合は、矩形中心を物理的なボール中心へ合わせる。

中心を合理的に判断できない場合は、無理に矩形を付けない。

### 滑らかさと正確性の違い

連続座標が滑らかであることは、ラベルの整合性を支持する材料になる。

ただし、同じ方向へ少しずつずれた誤ラベルも滑らかな軌道になるため、滑らかさだけでは正確性を証明できない。

今回の確認順序は次のとおりである。

    CSVの件数・フレーム範囲・可視性
    → フレーム間の座標差
    → 元画像への座標再描画
    → 人間による中心位置の確認

### モーションブラーとラベル不確実性

ボールの画面上の移動量が増えると、モーションブラーによって輪郭が伸びたり、ぼやけたりする。

人間が中心を判断できた場合でも、静止時より座標の不確実性が大きい可能性がある。

したがって、「矩形を付けられた」ことと「静止時と同じ精度で中心を決められた」ことを混同しない。

将来は、サーブ準備、トス、打球後、高速移動、遮蔽などの局面別にモデル誤差を確認する。

### ピクセル移動量の意味

フレーム間の画像上の移動量は、次の式で計算できる。

    distance = sqrt(delta_x^2 + delta_y^2)

これは画像平面上のピクセル移動量であり、実際の3次元速度ではない。

遠近、カメラ角度、奥行き方向の動き、アノテーション誤差が含まれるため、現段階では「画面上の移動量が増えた」と表現する。

`argparse`はPython標準ライブラリであり、コマンドライン引数の定義、解析、`--help`の自動生成を行う。追加インストールは不要である。

## 公式Datasetへ合わせるためのデータ整形

### ファイルが存在するだけでは互換にならない

公式コードが要求する列名とフォルダを用意しても、画像名の開始番号が違えば読み込めない。

今回の公式Datasetは、画像設定の生成時に`0.png`を直接開く。そのため、元画像名が`frame_002977.png`の場合は、学習用コピーを`0.png`へ変更する必要がある。

CSVの`Frame`も同じローカル番号へ変更する。

### 元番号とローカル番号

モデル互換性のための番号と、元動画へ追跡するための番号は役割が違う。

- ローカル番号：公式ローダーが画像を読むための0始まり番号
- 元フレーム番号：元動画の時刻と映像内容を追跡する番号

両方を保持するため、別の`frame_mapping.csv`を作る。

これにより、学習時のエラーや予測結果を元動画へ戻して確認できる。

### 実装を読むことで前提を修正する

CSV読込部分だけを見ると、元フレーム番号を画像名に使えるように見える。

しかし、画像設定生成部分は必ず`0.png`を要求していた。

一部のコードだけで設計を決めず、初期化、キャッシュ生成、実データ読込まで確認する必要がある。

### sliding stepと系列数

系列長を`L`、フレーム数を`N`、移動幅を`S`とする。

paddingなしで作れる完全系列数は、開始位置を`S`ずつ進め、最後まで`L`枚揃う範囲で決まる。

今回の条件では次のようになる。

- train：`N=128`、`L=8`、`S=1`なので121系列
- val：`N=120`、`L=8`、`S=8`なので15系列

trainは系列が大きく重複し、valは非重複になる。

系列数が多くても元画像の種類が増えたわけではないため、独立した121サンプルと解釈してはいけない。

### 背景中央値

公式実装は、ラリー内のフレームごとにピクセル中央値を計算し、`median.npz`へ可逆保存する。

試合中央値はラリー中央値の中央値として作られる。公式前処理では、同じ試合から分割したvalへtrainの試合中央値をコピーする。

VolleyScopeでもtrainとvalが同じ元動画・撮影条件なので、同じ中央値を使用する案が比較条件を揃えやすい。

ただし、train 128枚だけから作る中央値が最適という意味ではない。

### ブラーの観察と原因

valではtrainよりボールが荒く、モーションブラーが強く見えた。

一方、valの最大フレーム間移動量はtrainより小さかった。

したがって、「移動量が大きいからブラーが強い」とは結論づけられない。ピント、圧縮、ボールサイズ、照明、移動方向などの交絡要因を考える必要がある。
